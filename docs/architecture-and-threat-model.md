# Architecture and Threat Model

TrustChain + MediaTrace answers two separate questions and never mixes them up:

| Question | Module | Mechanism | Strength of answer |
|---|---|---|---|
| *Which registered item might this image come from?* | **MediaTrace** | SHA-256 lookup → pHash Hamming ranking → ORB + RANSAC | **Candidate only.** Similarity is never proof of origin. |
| *Is this registered record intact, and was it logged when and how it says?* | **TrustChain** | SHA-256, Ed25519, RFC 9162 Merkle log, signed checkpoints, independent witness | **Cryptographic**, under the trust assumptions below. |

The provenance-recovery workflow (`POST /trace/verify-candidate`) chains them. MediaTrace proposes a candidate, and TrustChain verifies the candidate's *registered original*. The response reports the **relationship** between the query and that original separately (`BYTE_IDENTICAL`, `PERCEPTUAL_CANDIDATE`, `GEOMETRIC_CANDIDATE` or `NONE`), so a perceptual match is never presented as proof of derivation.

## 2. Cryptographic design

### 2.1 Keys
There are three independent Ed25519 keypairs (PyNaCl / libsodium), generated by `scripts/generate_keys.py` into the git-ignored `keys/` directory and mounted read-only:

| Key | Holder | Signs |
|---|---|---|
| `custody` | api | custody events |
| `checkpoint` | api | Signed Tree Heads (checkpoints) |
| `witness` | witness only | witness acknowledgements |

`key_id = hex(SHA-256(public_key))[:16]`. The api pins the witness public key, and the witness pins the log's checkpoint key. In Docker, key auto-generation is disabled, so a missing key is a hard startup failure.

### 2.2 Signed statements
Every signature covers canonical JSON: keys sorted, `(",", ":")` separators, UTF-8, floats rejected. Each statement carries a `type` field for domain separation:

```text
custody event  {type:"trustchain-custody-event/v1", log_id, event_id, event_type, evidence_id, actor_id,
                timestamp, payload, prev_event_hash, key_id}
checkpoint     {type:"trustchain-checkpoint/v1", log_id, tree_size, root_hash, timestamp, key_id}
witness ack    {type:"trustchain-witness-ack/v1", log_id, tree_size, root_hash, log_signature,
                witness_timestamp, witness_key_id}
```

- `prev_event_hash` is the SHA-256 of the previous event for the same evidence, which forms a per-evidence hash chain.
- The registration payload contains the file's SHA-256. The *signed* event therefore binds the digest; the mutable `evidence.sha256_digest` column is cross-checked against it (`REGISTRATION_BINDING`).
- The backend, witness and CLI each build these bytes independently. A test asserts that all three produce byte-identical output.

### 2.3 RFC 9162 log
- **Leaf:** `SHA-256(0x00 ‖ canonical_event)`. **Node:** `SHA-256(0x01 ‖ L ‖ R)`. Split at the largest power of two below `n`.
- **Inclusion proofs** `PATH(m, D[n])` and **consistency proofs** `PROOF(m, D[n])` are generated in `app/crypto/merkle.py`. Verification follows RFC 9162 §2.1.3.2 and §2.1.4.2 exactly, and is implemented three times: backend, witness and CLI.
- **Test vectors:** RFC 9162 has no vector appendix, so the suite uses the Certificate Transparency reference vectors, which apply because RFC 9162 kept RFC 6962's hashing and proof formats. The suite also runs exhaustive self-consistency checks for every tree size from 1 to 33.
- **Appends** are serialised by an asyncio lock plus `pg_advisory_xact_lock`, so log indices are dense (0, 1, 2, …).
- **Append-only storage:** `custody_events` and `log_entries` are protected by SQLAlchemy `before_update`/`before_delete` guards and PostgreSQL triggers (migration `0002`). This was verified live: `UPDATE`/`DELETE` raises `table custody_events is append-only`.

### 2.4 Checkpoints and witness protocol
After each append, the api signs an STH and runs this exchange with the witness:

1. The api calls `GET /witness/latest` to learn the witness's last accepted size *m*.
2. The api sends `POST /witness/checkpoint` with the STH and `PROOF(m, D[n])`, authenticated by `X-Witness-Token`.
3. The witness checks, in order:
   1. The Ed25519 signature against the pinned log key; otherwise `BAD_LOG_SIGNATURE`.
   2. `n ≥ m`; otherwise `ROLLBACK`.
   3. For `n = m`, the root must equal the stored root. For `n > m`, the RFC 9162 consistency proof must verify against **the witness's own stored root**, never a root supplied by the log. Failure gives `EQUIVOCATION`.
4. On acceptance, the witness persists the checkpoint and returns a signed ack. The api verifies the ack with the pinned witness key before storing it.
5. On rejection, the witness persists a row with `status=REJECTED`, `alert_reason` and HTTP 409.

The witness has no shared code or database with the api. Witness downtime gives `witness_status=UNAVAILABLE`, which makes verification **INCONCLUSIVE** rather than PASS.

### 2.5 Verification (online and offline)

| Check | Online (`/evidence/{id}/verify`) | Offline CLI |
|---|---|---|
| Stored bytes match the registered SHA-256 (live MinIO re-hash) | `STORAGE_SHA256` | `FILE_SHA256` (the file you hold) |
| Digest bound by the signed registration event | `REGISTRATION_BINDING` | inside `FILE_SHA256` |
| Ed25519 on every event, key id, canonical form, hash chain | `EVENT_SIGNATURES`, `EVENT_HASH_CHAIN` | `CUSTODY_SIGNATURES` |
| Inclusion of every event in the signed tree | `MERKLE_INCLUSION` | `MERKLE_INCLUSION` |
| STH signature; consistency from the first witnessed STH | `CHECKPOINT_SIGNATURE` | `CHECKPOINT_AND_CONSISTENCY` |
| Witness co-signature(s) | `WITNESS_COSIGNATURE` | `WITNESS_COSIGNATURE` |

Overall: any FAIL gives FAIL; otherwise any INCONCLUSIVE gives INCONCLUSIVE; otherwise PASS. Keys embedded in a bundle are *claims*. Without `--log-key`, `--custody-key` and `--witness-key`, the CLI warns that it is only proving internal consistency.

## 3. MediaTrace

1. **Exact:** SHA-256 equality.
2. **pHash:** 64-bit DCT hash (ImageHash), computed after EXIF orientation normalisation. Candidates are ranked by Hamming distance and accepted if `d ≤ τ` (default 10).
3. **ORB:** OpenCV ORB with 1500 features at ≤800 px, Lowe ratio 0.75, and a RANSAC homography (reprojection 5 px). It runs on the top-K pHash neighbours (default 10) *regardless of τ*, and accepts a candidate with at least 15 inliers.

### Provenance recovery states

| State | Condition |
|---|---|
| `VERIFIED_REGISTERED_ORIGINAL` | A relationship exists and every check on the record passes |
| `CANDIDATE_ONLY` | A relationship exists, nothing failed, but something is INCONCLUSIVE (e.g. not yet witnessed) |
| `INTEGRITY_FAILURE` | A relationship exists and any check FAILED |
| `NO_MATCH` | No relationship (or the search returned nothing) |

The relationship is re-derived server-side from the uploaded query; client claims are never trusted. Each recovery verification is itself logged as a signed `EVIDENCE_VERIFIED` event.

### C2PA
`c2patool` (pinned v0.27.23 in the API image) runs as a subprocess with an argv list (no shell), a server-generated temp path, a timeout and a minimal environment. Results are normalised to `VALID` / `INVALID` / `ABSENT` / `ERROR`, plus signer, issuer, assertions and a `trusted` flag. This was validated against the real binary in the container: a file signed with c2patool's development certificate gives `VALID` (trusted = false); a one-byte modification gives `INVALID` (`assertion.dataHash.mismatch`); an unsigned file gives `ABSENT`. **ABSENT is never treated as evidence of manipulation.**

## 4. Threat model

**Assets:** registered originals; the custody history; the integrity of verification verdicts.

**Trust assumptions:**
- Private keys stay secret.
- The witness is operated independently of the log.
- Auditors obtain the log and witness public keys out-of-band.
- SHA-256 and Ed25519 are secure.

| # | Threat | Adversary | Mitigation | Detected by / evidence |
|---|---|---|---|---|
| T1 | Stored original altered or replaced in object storage | anyone with bucket credentials | SHA-256 bound in a signed, logged event; live re-hash | `STORAGE_SHA256` FAIL; demo scenario 2; `INTEGRITY_FAILURE` |
| T2 | DB row edited (digest or event changed) | DB admin / SQL injection | Signatures over canonical bytes; leaves in a signed tree; append-only triggers | `REGISTRATION_BINDING`, `EVENT_SIGNATURES`, `MERKLE_INCLUSION` FAIL; trigger raises |
| T3 | Forged custody event | insider without the custody key | Ed25519 on every event | CLI `CUSTODY_SIGNATURES` FAIL (test `test_cli_detects_forged_event`) |
| T4 | Event deleted or reordered (history rewrite) | compromised log operator | Merkle consistency; per-evidence hash chain; witness | witness `EQUIVOCATION`; `EVENT_HASH_CHAIN` FAIL |
| T5 | Log rollback (serve an older tree) | compromised log | witness keeps the max size seen | witness `ROLLBACK` alert (demo scenario 3a; 100% in benchmark 6) |
| T6 | Split view / equivocation (different trees to different parties) | compromised log **holding the checkpoint key** | witness checks consistency against its own stored root | `EQUIVOCATION` (demo 3b/3c; 100% in benchmark 6) |
| T7 | Forged checkpoint | attacker without the log key | pinned log key at witness and CLI | `BAD_LOG_SIGNATURE`; CLI FAIL |
| T8 | Bundle doctored to embed attacker keys | bundle in transit | CLI key pinning | CLI FAIL on pinned-key mismatch (`test_cli_rejects_wrong_pinned_key`) |
| T9 | Perceptual collision passed off as provenance | adversarial query | relationship reported separately; explicit "NOT proof" text | design invariant; FPR measured on negatives |
| T10 | Path traversal / unsafe file handling | uploader | UUID storage keys; magic-byte MIME; c2patool argv + temp path | — |
| T11 | Privilege misuse | auditor | role checks on every route (search / upload / transfer are INVESTIGATOR-only) | API tests |

**Out of scope / residual risk:**
- **Witness collusion.** A single witness colluding with the log defeats T4–T6. Multiple witnesses (a quorum) would mitigate this.
- **Key compromise.** There is no key rotation or revocation protocol. `key_id` makes rotation possible, but it is not implemented.
- **Wall-clock timestamps.** Timestamps are the signer's own clock; there is no RFC 3161 TSA.
- **Monitoring and gossip.** Clients do not gossip STHs with each other, so they rely on the witness.
- **Adversarial perceptual attacks.** Targeted pHash collisions or evasions are not defended. MediaTrace is a lead generator only.
- **Content truth.** SHA-256 proves integrity relative to registration, not that the content is true or was authentic at capture time.
- **Experiment C2PA coverage.** C2PA trust lists are not configured, so the signer is reported as `trusted=false` unless a trust anchor is supplied.
- **Single-process locks.** Append serialisation assumes a single api process; the PostgreSQL advisory lock covers multiple writers for appends, but checkpoint submission ordering assumes one api instance.
